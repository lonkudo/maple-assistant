fix: configured patrol range always drops from its top back to its first floor

The movement worker only entered the drop-to-first phase at the MAP-TOP final
layer and only when the profile's final_layer_action was drop-to-first.  With an
explicit patrol range [layer2, layer3] the range TOP (layer3) still carries a
mid-map rope, so the endpoint advance moved into the rope phase and the layer3
patrol repeated forever instead of dropping back to layer2 (the range first) -
exactly the "character patrols layer3 all the time" symptom.

- patrol_control: PatrolSnapshot now carries patrol_range_set (raw profile
  bounds both present), so the worker can tell an explicitly configured range
  from the full-map fallback.
- movement_worker: new _patrol_range_configured flag (constructor + patrol
  controller sync); _route_target and _advance_route_endpoint treat the RANGE
  TOP as the final layer for the drop - an explicitly configured range always
  drops to its first floor (range [2,3] -> layer3 patrol done -> drop to
  layer2 -> restart), while an unconfigured map keeps the legacy final-layer
  action behaviour.
- test_movement_worker: range-top-drop (configured) and legacy-repeat
  (unconfigured) regression tests.
