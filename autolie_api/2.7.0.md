# RoiTrack 客户端发包规范（v2.7.0）

> 面向客户端实现：WebSocket 发帧 + HTTP 同步 POST。  
> 完整服务端说明见同目录 `PROTOCOL.md`；Python 联调见发行包 `examples/test_v27_client.py`。

---

## 1. 版本与端点

| 项 | 值 |
|----|-----|
| 协议版本 | **2.7.0**（`handshake_ack.server_version` / HTTP health） |
| WS 默认 | `ws://<host>:8001` |
| HTTP 默认 | `http://<host>:8002`（= WS 端口 +1；`http_port=0` 时自动） |
| ROI 尺寸 | **372 × 248**（BGR，与训练一致） |
| JPEG | **quality=90**，三通道彩色 |
| 坐标系 | `roi_top_left`：原点 ROI 左上角，x 向右，y 向下 |
| 客户端必填 | **`product_key`**（LIE 密钥）；**不传**授权服地址 |

---

## 2. 两种运算模式

握手时 `mode` 选定，**同连接不可混用**。

| 模式 | 握手 `mode` | 客户端发 | 服务端 | 计费 kind |
|------|-------------|----------|--------|-----------|
| **推理**（默认） | 省略或 `infer` | JPEG ROI | ONNX + 追踪 | `lie3`，默认 1 次/轮 |
| **追踪** | `track` | 点云 `points` | 仅追踪（无 ONNX） | `lie3_track`，默认 0.5 次/轮 |

### 计费与轮次

- **握手不扣次**；`probe` 探测也不扣次。
- **首张有效帧**（`frame` / `frame_coords` / HTTP 首帧 POST）触发开轮并扣次。
- 轮内后续帧**不额外扣次**。
- **`round_sec` 仅读服务端配置**（GUI / config.json）；WS 握手勿传；HTTP 创建 session 可传但服务端以配置为准。
- **`frame_standard`**：客户端传 **3 / 4 / 5 / 6 / 7**（≈ 对应 fps），用于追踪 jump/残差等参数缩放；**不限制**每轮发帧数量。

---

## 3. 通用：`frame_id` 规则

| 规则 | 说明 |
|------|------|
| 起始 | 每轮从 **1** 开始（`round_end` / `reset` 后重置） |
| 递增 | 必须连续：1, 2, 3, …（不可跳号、不可重复） |
| 发帧节奏 | **不必**等 `frame_result` 再发下一帧（可 burst） |
| 服务端 | 按 `frame_id` **升序** infer；`frame_result` **同序**返回 |
| 超前缓冲 | fs7/fs6 ≤ **4** 帧；fs5/fs4 ≤ **3** 帧；fs3 ≤ **2** 帧；超限 → `frame_buffer_full` |

```text
客户端                         服务端
  │  frame id=1,2,3… (burst)
  ├──────────────────────────►  入队 → 按 1→2→3 infer
  ◄──────────────────────────   frame_result id=1
  ◄──────────────────────────   frame_result id=2
  ◄──────────────────────────   …
```

## 4. WebSocket 流程

### 4.1 连接超时

| 阶段 | 默认 | 说明 |
|------|------|------|
| TCP 连上后 | **10s** | 须发 `handshake` 或 `probe`，否则踢 |
| 正式握手后 | **10s** | 无有效帧活动踢（burst 入队/drain 期间会续期） |

### 4.2 正式握手（推理 / 追踪）

**发送（JSON text）：**

```json
{
  "type": "handshake",
  "product_key": "LIE-TW-xxxx",
  "mode": "infer",
  "frame_standard": 7,
  "image_transport": "bgr_jpeg90_packed",
  "client_info": "my_client_v1"
}
```

| 字段 | 必填 | 说明 |
|------|------|------|
| `type` | 是 | 固定 `"handshake"` |
| `product_key` | 是 | LIE 密钥 |
| `mode` | 否 | `infer`（默认）或 `track` |
| `frame_standard` | 否 | 3–7，默认 7；兼容别名 `frames_per_round` |
| `image_transport` | 否 | 推理发图方式，见 §5；兼容别名 `image_format` |
| `client_info` | 否 | 客户端标识（日志） |
| `round_start` | 否 | 兼容字段，**不再在握手扣次** |
| `round_sec` | — | **勿传** |

**`image_transport` 取值（推理模式）：**

| 值 | 内部 | 发帧方式 |
|----|------|----------|
| `bgr_jpeg90_base64` / `base64` | base64 | JSON + base64 字符串 |
| `bgr_jpeg90_binary` / `binary` | binary | JSON 元数据 + binary JPEG（双包） |
| `bgr_jpeg90_packed` / `packed` / `rtf1` | packed | **RTF1 单包 binary（v2.7 推荐）** |

追踪模式仅 JSON 发 `points`，**不支持** binary / packed。

**成功响应 `handshake_ack`（节选）：**

```json
{
  "type": "handshake_ack",
  "status": "ok",
  "server_version": "2.7.0",
  "session_id": "123456789",
  "auth": true,
  "quota_left": 99,
  "round_active": false,
  "billing": "first_frame",
  "mode": "infer",
  "frame_standard": 7,
  "image_transport": "packed",
  "config": {
    "roi_size": [372, 248],
    "jpeg_quality": 90,
    "coord_space": "roi_top_left",
    "max_frame_b64_chars": 71680,
    "max_frame_bytes": 53760,
    "round_sec": 60,
    "consume_per_round_infer": 1,
    "consume_per_round_track": 0.5,
    "app_handshake_timeout_sec": 10,
    "idle_no_frame_sec": 10
  }
}
```

**失败：** `{ "type": "auth_denied", "message": "...", "success": false }` → 连接关闭。

### 4.3 探测握手 `probe`（选服，不鉴权）

```json
{ "type": "probe", "client_info": "picker_v1", "client_ts": 1735689600.123 }
```

或 `{ "type": "handshake", "mode": "probe", ... }`。

响应含 `load.slots_left`、`load.last_frame_ms` 等；**不能发帧**，须再发正式握手。

## 5. WebSocket 发帧（推理模式）

三种上行格式任选（握手声明后建议固定一种）。单帧 JPEG 上限 **`max_frame_bytes`**（默认 **53760**）；base64 上限 **`max_frame_b64_chars`**（默认 **71680**）。

### 5.1 base64（兼容旧客户端）

**JSON text：**

```json
{
  "type": "frame",
  "frame_id": 1,
  "image": "<base64 JPEG>",
  "frame_interval_sec": 0.14
}
```

| 字段 | 必填 | 说明 |
|------|------|------|
| `frame_id` | 是 | 从 1 连续递增 |
| `image` | 是 | base64 JPEG q90 |
| `frame_interval_sec` | 否 | 与上帧间隔（秒）；影响 jump 时间缩放 |

### 5.2 RTF1 单包 binary（**推荐**）

**一条 WebSocket binary 消息**，布局（小端 uint32）：

```text
[4B magic "RTF1"][4B frame_id][4B json_len][4B jpeg_len][json_len B JSON UTF-8][jpeg_len B JPEG]
```

JSON 元数据（无 `image` 字段）示例：

```json
{
  "type": "frame",
  "frame_id": 1,
  "frame_interval_sec": 0.14
}
```

- magic 必须为 ASCII `RTF1`
- 整包长度须精确等于 `16 + json_len + jpeg_len`
- 服务端仍用 **JSON text** 回 `frame_result`
- 解码失败 → `error: bad_rtf1`

**打包参考（Python）：** `mxd_lie_runtime.ws_roi_frame_pack.pack_rtf1(frame_id, meta, jpeg_bytes)`

### 5.3 binary 双包（v2.6 兼容）

1. **JSON text**（无 `image`）：

```json
{
  "type": "frame",
  "frame_id": 1,
  "jpeg_binary": true,
  "frame_interval_sec": 0.14
}
```

2. **紧接一条 binary**，payload = 原始 JPEG 字节。

握手已声明 `bgr_jpeg90_binary` 时可省略 `"jpeg_binary": true`。若上一条 JSON 的 binary 未收齐就发新帧 → `binary_frame_pending`。

## 6. WebSocket 发帧（追踪模式）

握手 `"mode": "track"`。发 **`frame`** 或 **`frame_coords`**（等价）：

```json
{
  "type": "frame_coords",
  "frame_id": 1,
  "points": [[186.0, 125.0, 0.92], [100.5, 80.2, 0.88]],
  "frame_interval_sec": 0.14
}
```

| 字段 | 必填 | 说明 |
|------|------|------|
| `frame_id` | 是 | 同推理模式 |
| `points` | 是 | `[[x,y] 或 [x,y,conf], ...]`，坐标在 372×248 ROI 内 |
| `frame_interval_sec` | 否 | 同推理模式 |

- 点须在 `0 ≤ x < 372`、`0 ≤ y < 248`；否则该点丢弃；全无效 → `bad_points`
- 单帧通常 < 2KB（无 JPEG）

---

## 7. WebSocket 收包：`frame_result`

每条处理完的帧返回 **JSON text**：

```json
{
  "type": "frame_result",
  "frame_id": 1,
  "success": true,
  "mode": "infer",
  "x": 186.0,
  "y": 125.0,
  "x_main": 372.0,
  "y_main": 250.0,
  "main_wh": [745, 496],
  "decision": "track",
  "onnx_count": 14,
  "parsed_count": 12,
  "api_ok": true,
  "half_mode": true,
  "timing_ms": 25.3,
  "frame_standard": 7,
  "queue_depth": 0,
  "frames_in_round": 1,
  "quota_left": 98,
  "seconds_left": 55.2,
  "round_active": true
}
```

| 字段 | 说明 |
|------|------|
| `success` | 是否给出可用坐标（hold 帧可能仍为 true） |
| `x` / `y` | **协议半幅 ROI (372×248)** 内目标坐标 |
| `x_main` / `y_main` | lie3main **745×496** 坐标 |
| `decision` | `track` / `hold_prev` / `freeze_search_only_static` / `abandon_frame_hold` 等 |
| `onnx_count` | 推理模式：ONNX 检测数；追踪模式：`null` |
| `parsed_count` | ROI 内有效点数 |
| `api_ok` | 推理模式：本帧 ONNX 是否成功；追踪模式：点云是否非空 |
| `api_skip_reason` | 如 `zero_pivot_points`、`local_onnx_failed` |
| `queue_depth` | 可选；发出本 result 时仍排队的后续帧数 |
| `timing_ms` | 本帧服务端处理耗时 |
| `error` | 失败时错误码（见 §9） |

**客户端注意：** `success=true` 且 `decision=abandon_frame_hold` 表示 hold 上一帧坐标；**不要**把 `api_ok=false` 一律当致命错误（须结合 `decision`）。

## 8. WebSocket 控制消息

| 发送 | 说明 | 响应 |
|------|------|------|
| `{ "type": "round_end" }` | 结束本轮，清空 tracker | `{ "type": "round_ended", "success": true }`；下轮 `frame_id` 从 1 重计 |
| `{ "type": "reset" }` | 重置 tracker，不开轮 | — |
| `{ "type": "reset", "round_start": true, "product_key": "..." }` | 重置并准备新开轮（扣次仍等首帧） | — |
| `{ "type": "round_start", ... }` | 兼容；开轮仍由首帧触发 | — |

---

## 9. 错误码

| `error` | 含义 | 客户端建议 |
|---------|------|------------|
| `missing_frame_id` | 未传 `frame_id` | 每帧必带递增 id |
| `bad_frame_id` | 非整数 | 修正类型 |
| `frame_id_stale` | id 小于已处理进度 | 忽略或 `round_end` 重开 |
| `frame_id_duplicate` | 同 id 已在队列 | 勿重发 |
| `frame_buffer_full` | 超前超过缓冲上限 | 暂停发帧或降低 burst |
| `binary_frame_pending` | 双包模式 binary 未配对 | 改 RTF1 或成对发送 |
| `bad_rtf1` | RTF1 格式/长度错误 | 检查 magic 与长度 |
| `image_too_large` | JPEG/base64 超限 | 压缩 ROI |
| `bad_points` | 追踪点云非法或全越界 | 检查 `points` |
| `missing points` / `missing image` | 缺必填字段 | 补全 payload |
| `round_inactive` | 轮已结束 | 发帧开轮或 `round_end` 后重开 |
| `quota_exceeded` | 配额不足 | 换 key / 充值 |

拒收类（如 `frame_buffer_full`）**立即**返回，不入队。

## 10. HTTP 同步帧（v2.7+）

适用于不便用 WebSocket 的客户端：**每帧一次 POST，同一次响应返回坐标**。

| 项 | 值 |
|----|-----|
| 地址 | `http://<host>:8002` |
| Session TTL | 默认 **45s**（有帧活动续期） |
| 吞吐 | ≈ **1 / infer 时延**（如 200ms infer ≈ 5fps 上限）；高帧率请用 WS + RTF1 burst |
| 追踪模式 | **当前未支持** HTTP track（返回 400） |

### 10.1 健康检查

```http
GET /v1/health
```

```json
{ "ok": true, "service": "roi-track-http", "mode": "sync", "server_version": "2.7.0" }
```

### 10.2 创建 Session

```http
POST /v1/track/session
Content-Type: application/json

{
  "product_key": "LIE-TW-xxxx",
  "frame_standard": 7,
  "round_sec": 60
}
```

**200 响应：**

```json
{
  "success": true,
  "session_id": "<32位hex>",
  "expires_at": 1735689645.0,
  "session_ttl_sec": 45,
  "frame_standard": 7,
  "server_version": "2.7.0",
  "roi_size": [372, 248],
  "billing": "first_frame",
  "frame_api": "sync"
}
```

### 10.3 同步发帧

```http
POST /v1/track/session/{session_id}/frame
Content-Type: image/jpeg
X-Frame-Id: 1
X-Frame-Interval: 0.14

<原始 JPEG 字节>
```

| Header | 必填 | 说明 |
|--------|------|------|
| `Content-Type` | 是 | `image/jpeg` |
| `X-Frame-Id` | 是 | 从 1 连续递增 |
| `X-Frame-Interval` | 否 | 与上帧间隔（秒） |

**200 响应：** 字段与 WS `frame_result` 一致（JSON body）。

**乱序：**

- `X-Frame-Id` **大于**期望 id：中间缺失帧按 **hold** 合成，响应可含 `"gap_filled": [ ... ]`
- id **小于**期望 → **409** `frame_id_stale`

**HTTP 客户端必须串行等回包**：上一帧 POST 未完成前勿发下一帧，否则客户端侧会出现「等待回包 / pending」类逻辑问题。

### 10.4 结束 Session

```http
DELETE /v1/track/session/{session_id}
→ { "success": true }
```

## 11. 客户端实现清单

### 推荐组合（高帧率）

1. WS 连接 → 握手 `image_transport: bgr_jpeg90_packed`
2. 每帧 `pack_rtf1(frame_id, meta, jpeg)` 一条 binary 发出
3. 可 burst；按序收 `frame_result`
4. 轮末发 `round_end`

### 最低兼容

1. WS → 握手默认 base64
2. 每帧 JSON `{ type, frame_id, image }` → 等 `frame_result` → 下一帧

### 图像预处理

- 裁剪/缩放到 **372×248** BGR
- `cv2.imencode(".jpg", bgr, [IMWRITE_JPEG_QUALITY, 90])`
- 勿发 PNG / 灰度（旧版 `gray_png_base64` 仅 legacy）

### 坐标使用

- 鼠标/执行层一般用 **`x` / `y`**（372×248 协议 ROI）
- 需要与本地 lie3main 对齐时用 **`x_main` / `y_main`**
